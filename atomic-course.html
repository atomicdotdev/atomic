Module 1

The problem Git didn't see coming

Imagine you ask Claude to fix a bug. It edits three files. How do you know which model wrote what? How much did it cost? If two agents edited the same line — who wins? Git was designed before these questions existed.

Git's mental model
📜
A necklace of snapshots
Git stores your project's history as a chain of commits. Each commit is a snapshot of every file. To find what changed, Git compares two snapshots line by line.
🔢
Lines are the atom
In Git, the smallest unit of change is a line of text. If two people edit the same line — even different words on that line — Git sees a merge conflict and makes you resolve it by hand.
⚡ Why this worked for 20 years
When humans write code, they rarely edit the exact same line at the same time. Git's line-based model was good enough. AI changed the math — multiple agents can touch the same files in the same session, simultaneously, at high speed.
Where Git breaks with AI
QuestionGit's answerWhat you actually need
Which model wrote this? Nothing — a human has to add a "Co-authored-by" note by hand Model name, vendor, session ID embedded in the change itself
How much did this session cost? Not tracked — you need an external dashboard Token counts and USD cost stored in every change
Two agents edit the same line Merge conflict — someone resolves it manually If they touched different tokens, it merges automatically
Agent isolation Branches diverge — messy history, orphaned commits Stacks: lightweight views of the same graph, zero cleanup needed
File renamed + history Heuristic guessing — can break history Inode tracking — renames are always exact, history is unbroken
Enter Atomic
🧮
Graph, not lines
Files are stored as a DAG of content chunks. Two agents editing different parts of a file create independent nodes — no conflict possible.
🔏
AI attribution is structural
Every change carries vendor, model, session, turn number, token count, and cost. It's part of the change's cryptographic hash, so it can't be tampered with.
📐
Mathematically correct merges
Independent changes always merge cleanly — not by heuristic guessing, but by proof. If change A and change B touch different nodes, applying A then B gives the same result as B then A. Commutative by design.

Network operations. Handles push, pull, and clone over HTTP. Compares Merkle states to find missing changes, then uploads or downloads them.
💡 Why split into 7 crates?
Each crate can be used independently. A tool that only needs to read change files can depend on atomic-core without pulling in the full CLI. This modularity also means the engine can be embedded in editors, IDEs, or AI coding tools that want native Atomic support.

Module 3

Files as graphs — the big idea

This is the central insight that makes everything else possible. Git sees a file as a list of lines. Atomic sees it as a web of connected content chunks. That one difference changes everything about how conflicts, history, and merges work.

The metaphor: a Wikipedia article
📋
Git's view: a numbered list
Imagine a Wikipedia article as a numbered list of sentences. Line 42 is always "sentence 42". To change it, you rewrite that line. If two people edit line 42, there's a conflict — even if they changed different words in the sentence.
🕸️
Atomic's view: a web of nodes
Now imagine the article as a web of connected passages. Each passage has a unique identity — not a line number, but an ID. To add a new sentence, you insert a new node and connect it between existing nodes. The order emerges from the connections.
⚡ Why this is powerful
When content has a unique identity (not just a position), you can move it, delete it, and reference it from anywhere — and history always knows exactly what happened to it. Two changes inserting different nodes never conflict because they're creating new independent things, not competing to own the same position.
Vertices: the nodes
pub struct GraphNode<H> {
    /// The change that introduced this node
    pub change: H,
    /// Start position in the change's content
    pub start: ChangePosition,
    /// End position (exclusive)
    pub end: ChangePosition,
}
Plain English
1Define a node in the content graph. The <H> means it can hold either an internal ID or an external hash — same shape, different uses.
3change — which recorded change first introduced this piece of content. Every node knows its origin.
5start — where in that change's byte buffer this content begins (inclusive).
7end — where the content ends (exclusive). Together, start+end slice out the exact bytes from the change file.
Edges: the connections
pub struct EdgeFlags: u8 {
    /// Connects sequential content in a file
    const BLOCK   = 0b0000_0001;
    /// Computed edge (not stored in changes)
    const PSEUDO  = 0b0000_0100;
    /// Connects directories to their children
    const FOLDER  = 0b0001_0000;
    /// Reverse direction of another edge
    const PARENT  = 0b0010_0000;
    /// Content removed — stays in graph
    const DELETED = 0b1000_0000;
}
Plain English
1Each edge has a set of flags — like tags that describe what the edge means. Multiple flags can be combined (e.g., a deleted folder edge).
3BLOCK — "this content comes right after that content in the file." The most common edge type.
5PSEUDO — a helper edge the system computes to maintain graph structure. Not written by users or agents.
7FOLDER — represents directory structure. A folder node connects to all files it contains.
9PARENT — the reverse direction. Every forward edge has a corresponding parent edge, enabling fast backwards traversal.
11DELETED — marks removed content. The node stays in the graph — only the edge is flagged. This is how history is preserved forever.
Visualizing the graph
Blue nodes = alive content  ·  Dashed orange = DELETED (stays in graph)  ·  Arrows = BLOCK edges (ordering)

Module 4

The recording pipeline

Imagine you just edited a file and run atomic record -m "fix the bug". What actually happens? The system goes through six steps — from detecting the change on disk to updating the graph in the database. Let's trace each one.

Step by step
1
Detect
Scan the working copy. Compare file inodes and modification times against the tracked list. Output: a list of modified, added, and deleted files.
detect.rs
↓
2
Load pristine content
For each modified file, traverse the graph to reconstruct what the file looked like at the last recorded state. This is the "before" side of the diff.
output.rs
↓
3
Diff
Compare pristine content (before) with working copy content (after). Uses the Myers or Patience algorithm (your choice). Output: a sequence of operations — "keep lines 1-5, replace line 6, keep lines 7-20."
diff/
↓
4
Build atoms
Convert diff operations into graph operations. New content becomes Insertion atoms (new nodes + edges). Removed content becomes EdgeUpdate atoms (add DELETED flag to existing edges). Each atom targets specific vertices in the graph.
builder.rs
↓
5
Hash & store
Serialize the change to binary (Format v3). Run Blake3 over the bytes to produce a hash. Store the file at .atomic/changes/{first2}/{rest} — the path is derived from the hash.
changestore.rs
↓
6
Apply to graph
Write the change's operations into the redb database. New nodes are added. Edges are updated. The stack's Merkle state is updated.
apply/
What a change looks like
Two kinds of atoms

Insertion — new content enters the graph. Contains: the bytes of new content, pointers to neighboring nodes (predecessors and successors), and the inode of the file.

EdgeUpdate — existing edges get new flags. Mainly used for deletions: find the edges pointing to removed content, add the DELETED flag.

Content-addressed storage
.atomic/
  changes/
    AB/
      CDEF1234...
    RI/
      E62WWC2WXH
    CD/
      EFGHIJKL...

The first 2 chars of the hash become a directory — like a filing cabinet with 256 drawers. Two identical changes always land in the same file.

💡 Two-way sync: redb ↔ .change files
The redb database and .change files are two sides of the same coin. redb is how Atomic reads and writes changes locally — fast, transactional, queryable. The .change file format is how changes and provenance travel across the network during push and pull. import_v3_file brings a received file into redb; export_v3_file serializes from redb to send out. The hash is shared between both — same data, same fingerprint, whichever form it's in.

Module 5

AI DNA — provenance in every change

Every change Atomic records can carry a complete chain of custody: which AI model, which vendor, which session, which turn, how many tokens, what it cost. This data is embedded in the change's cryptographic hash, making it tamper-evident.

The chain of custody metaphor
🔗
Who did it
Vendor (Anthropic, OpenAI, Google) + model name + session ID. Unambiguous attribution, verified by the change hash.
🕐
When & how long
Session start/end timestamps, turn number, and duration in milliseconds. Reconstruct the exact timeline of an AI session.
💰
What it cost
Input tokens, output tokens, cache tokens, and cost in USD. Audit any team's AI spending change by change.
The Provenance struct
let provenance = Provenance::builder()
    .vendor(AIVendor::Anthropic)
    .model("claude-sonnet-4-20250514")
    .tool(AITool::Editor("zed".to_string()))
    .suggestion_type(SuggestionType::Collaborative)
    .prompt_hash("ABCDEF...")
    .input_tokens(1500)
    .output_tokens(500)
    .cost_usd(0.015)
    .build();
Plain English
1Start building a provenance record. Uses the "builder pattern" — set each field, then build at the end.
2vendor — the AI company. An enum so names are consistent: Anthropic, OpenAI, Google, Meta, etc.
3model — the specific model version. Exact string, so history shows "claude-sonnet-4-20250514" not just "Claude."
4tool — how the AI was invoked. Was it a CLI tool, an editor plugin, a direct API call?
5suggestion_type — collaborative (AI + human) vs autonomous (AI alone).
6prompt_hash — a fingerprint of the prompt, not the prompt itself. Preserves privacy while still allowing verification.
7–8input/output_tokens — exact token counts for cost accounting and capacity planning.
9cost_usd — what this specific change cost in dollars. Sum across all changes to audit spending.
The session envelope

Provenance tracks per-turn metrics. The SessionEnvelope adds the session-level context — linking individual turns into a coherent session timeline.

let envelope = SessionEnvelope::builder(
    "session-abc", "claude-code"
)
.turn_number(3)
.agent_display_name("Claude Code")
.prompt_summary("Fix the auth bug")
.files_in_turn(vec![
    "src/auth.rs".to_string(),
    "src/auth_test.rs".to_string()
])
.turn_duration_ms(12400)
.build();
Plain English
1–3Create a new session envelope. Takes the session ID and agent identifier — the two pieces needed to group turns together.
4turn_number — this is the 3rd turn in this session. Lets you reconstruct the chronological sequence of what the AI did.
5agent_display_name — human-readable name for audit logs and dashboards.
6prompt_summary — a short description of what the user asked for in this turn.
7–10files_in_turn — which files the agent touched during this turn. Links changes back to specific files.
11turn_duration_ms — how long this turn took. 12,400ms = 12.4 seconds. Useful for performance analysis.
🔏 Why it can't be faked
The Provenance struct and SessionEnvelope both live in the hashed portion of the change. That means they're included in the input to the Blake3 hash function. Change vendor from "anthropic" to "openai" after recording — the hash changes. Since the hash is the change's identity and storage path, a tampered change is a completely different change. The original, untampered change still exists at the original hash.

Module 6

Stacks, storage & identity

The last pieces: how Atomic organizes parallel work without branches, how it syncs with remotes efficiently, and how your identity is cryptographically tied to your changes.

Stacks vs branches
🌿
Git branches: diverging timelines
When you branch in Git, you create a separate copy of the change history. Work diverges. To reconcile, you need a merge commit — often with conflicts. Orphaned commits can accumulate.
📚
Atomic stacks: shared graph, separate logs
All stacks point to the same underlying graph. Creating a stack just adds a new entry in a table: "stack name → list of changes + Merkle state." Zero data duplication. When you delete a stack, it cascade-deletes its edges — no orphaned history.
$ atomic stack new experiment --from main Stack 'experiment' created (parent: main) # No files copied. No data duplicated. # Just a new pointer to the same graph. $ atomic stack list main [42 changes] state: 8f3a2c... * experiment [42 changes] state: 8f3a2c... # Same state hash — they start identical. $ atomic stack delete experiment Stack 'experiment' deleted. 0 orphaned nodes. # Cascade-deleted experiment's edges. Graph stays clean.
💡 Why agents love stacks
When an AI agent starts a session, Atomic automatically creates an isolated stack for it. The agent works freely on its stack without touching main. When done, changes are applied to the parent stack — or discarded. No merge commits. No branch cleanup. No orphaned history from abandoned sessions.
Merkle states for fast sync
🔢
How Merkle state works

After each change, the stack's state is updated:

new_state = Hash(
  old_state || change_hash
)

The final state is a fingerprint of the entire history. Two stacks with the same Merkle state have identical histories.

⚡
Fast sync protocol

On atomic push:

  1. Compare local Merkle state with remote
  2. Same state? Already in sync, done
  3. Different? Walk back until common ancestor
  4. Upload only the changes the remote is missing

No need to compare every file — one hash comparison tells you if sync is needed.

Cryptographic identity
🗝️
Your keypair
When you first run Atomic, it generates an Ed25519 keypair. Your private key signs every change you record. Your public key travels with the change, so anyone can verify it was really you.
🤖
Agent identity
AI agents get a delegated identity derived from your keypair. The author tag format is agentname+sessionhash <you@email.com> — so changes are attributed to both the agent and you. You remain the root of trust.
🔎
Attestations
When a session ends, Atomic creates an attestation — a graph-level audit node covering the entire session: total cost, tokens, models used, and which changes it covers.
$ atomic agent attest XMJZ3IPF Claude Code · claude-sonnet-4-5 12.4k tokens · 3m 42s · 2 changes R3KQP7YN Claude Code · claude-sonnet-4-5 8.1k tokens · 1m 15s · 1 change ──────────────────────────────────── Total: $0.12 · 3 changes · 20.5k tokens
